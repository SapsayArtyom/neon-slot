# Neon Lines — слот и SDK

Классический слот 5×3 на десять линий и переиспользуемый SDK, на котором строятся
другие слот-игры. TypeScript, Pixi.js, Vite, GSAP.

## Запуск

Нужен **Node.js 22.12 или новее** (требование Vite 8).

```bash
npm install     # установка
npm run dev     # разработка, http://localhost:5173
npm run build   # сборка в dist/ (с проверкой типов)
npm run preview # проверка собранной версии
npm run lint    # ESLint
npm run format  # Prettier
```

Сборка кладёт относительные пути, поэтому `dist/` работает и в корне домена,
и в подпапке — например, на GitHub Pages.

## Правила игры

Поле 5×3, десять фиксированных линий выплат.

**Линии.** Считаются слева направо начиная с первого барабана: нужно 3, 4 или 5
одинаковых символов подряд. Выплата — множитель **полной ставки** (не ставки на
линию: так в игре на одно понятие меньше). Платит только самая длинная
комбинация на линии.

**Wild** заменяет любой символ кроме Scatter и платит сам. Линия, начинающаяся
с Wild, может оплатиться и как линия Wild, и как линия первого обычного
символа — засчитывается то, что выгоднее игроку.

**Scatter** по линиям не платит, но считается в любом месте поля. Три и более
Scatter дают **6 фриспинов**.

**Фриспины.** Ставка внутри раунда фиксирована — та, на которой он выигран.
Каждый Wild, выпавший во фриспинах, **залипает** и остаётся на своей клетке до
конца раунда, поэтому каждый следующий спин дороже предыдущего. Scatter внутри
раунда новых спинов не добавляет.

### Таблица выплат

Множители полной ставки за 3 / 4 / 5 символов подряд:

| Символ | 3   | 4   | 5   |
| ------ | --- | --- | --- |
| WILD   | 13  | 54  | 270 |
| CORE   | 9   | 32  | 135 |
| PRISM  | 5   | 16  | 60  |
| ORB    | 3   | 10  | 35  |
| A      | 2.2 | 5.5 | 17  |
| K      | 1.7 | 4.5 | 13  |
| Q      | 1.2 | 3   | 10  |
| J, 10  | 0.8 | 2.5 | 6   |

Ставки: 0.2 / 0.5 / 1 / 2 / 5 / 10. Стартовый баланс 1000.

### Характеристики

Замерены симуляцией на 500 000 оплаченных спинов — через ту же функцию
`playSpin`, которая обслуживает игру:

| Отдача | Частота выигрыша | Частота бонуса | Доля бонуса в отдаче |
| ------ | ---------------- | -------------- | -------------------- |
| 96.3%  | 27.0%            | 1 к 70         | 26%                  |

Число фриспинов выбрано по этим же замерам: при восьми бонус давал бы 42% всей
отдачи, и триггер пришлось бы делать вдвое реже.

### Управление

|                 |                                                           |
| --------------- | --------------------------------------------------------- |
| SPIN или пробел | крутить; во время спина — досрочная остановка             |
| «–» и «+»       | ставка, только между спинами                              |
| TURBO           | барабаны встают одновременно и почти сразу                |
| AUTO            | спины идут подряд, пока не выключить или пока есть деньги |

Мышь и касания обрабатываются одинаково: Pixi сводит их к событиям pointer.

## Архитектура

Три слоя, граница между ними явная.

```
src/
├─ sdk/              движок: ничего не знает о конкретной игре
├─ games/neon-lines/ игра: правила, арт, конфиг
└─ main.ts           точка входа: знает только контракт GameDefinition
```

**Граница SDK → игра проверяется линтером.** В `eslint.config.js` для файлов
`src/sdk` запрещены импорты из `games`. Обратное направление идёт только через
алиас: игра пишет `import { ... } from '@sdk'`, поэтому граница видна в каждом
файле игры.

### Что в SDK

| Модуль   | Содержимое                                                                   |
| -------- | ---------------------------------------------------------------------------- |
| `app`    | `GameApp` — цикл кадра и отслеживание размеров; `Viewport`; `GameDefinition` |
| `scene`  | `Scene` и `SceneManager`                                                     |
| `layout` | `place`, `applyLayout`, `LayoutScheme` — вся адаптивность                    |
| `assets` | `loadAssets` и манифест ресурсов                                             |
| `reels`  | `Reel`, `ReelSet`, `WinOverlay`, тип `SymbolView`                            |
| `flow`   | `SpinController` — цикл одного спина и его состояние                         |
| `api`    | контракт `SpinService`, `SpinOutcome`, генератор случайных чисел             |
| `ui`     | `Button`, `ToggleButton`, `ValueCounter`, `onKeyPress`                       |
| `fx`     | такт анимаций и `tweenTo`                                                    |

SDK намеренно не знает, что такое линия выплат, кластер или Wild. Он умеет
крутить сетку, остановить её на присланном поле и подсветить указанные клетки —
поэтому тот же SDK примет и кластерную игру, и ways.

### Что в игре

| Папка     | Содержимое                                                              |
| --------- | ----------------------------------------------------------------------- |
| `config/` | символы, линии, таблица выплат, ленты, ставки, тема, раскладка, ресурсы |
| `math/`   | чистые функции: `evaluateLines`, `spin`, `freeSpins`, `round`           |
| `api/`    | `MockSpinService` — источник результатов                                |
| `state/`  | `Wallet` и доступность кнопок                                           |
| `ui/`     | блоки интерфейса, собранные из компонентов SDK                          |
| `view/`   | текстуры символов и спрайт                                              |
| `scenes/` | `GameScene` и `LoadingScene`                                            |

### Ключевые решения

**Результат спина целиком считает «сервер».** `MockSpinService` возвращает
готовое поле, выигрыши и состояние раунда фриспинов, а клиент только
проигрывает присланное. Незавершённый раунд тоже хранится в сервисе, как в
настоящей игровой сессии. Поэтому замена мока на HTTP-клиент не затрагивает
игру: контракт `SpinService` тот же.

**Математика — чистые функции.** `playSpin` принимает состояние раунда
аргументом и возвращает новое. Та же функция обслуживает игру и расчёт
отдачи, так что разойтись им негде.

**Анимациями владеет GSAP, но такт ему задаёт Pixi.** Собственный цикл GSAP
отключён, время приходит из тикера Pixi с приоритетом `HIGH`, то есть до
отрисовки. Один источник времени вместо двух: порядок «раскладка → анимации →
рендер» гарантирован, и анимации встают вместе с игрой.

**ECS не используется.** Слот — это конечный автомат плюс дерево отображения,
а не множество однородных сущностей. ECS добавил бы косвенность без выгоды.
Вместо него композиция и конфиг в виде обычных данных.

## Как создать новую игру

Контракт — два поля:

```ts
export type GameDefinition = {
  background: number // нужен до создания первой сцены
  start(app: GameApp): Promise<void> // всё остальное игра делает сама
}
```

Порядок работы:

1. Создать `src/games/<id>/` и описать в `config/` символы, ленты, выплаты и
   раскладку — это обычные данные, кода там нет.
2. Написать правила в `math/` чистыми функциями.
3. Реализовать `SpinService`: он возвращает `{ grid, totalWin, ... }`.
4. Собрать сцену, унаследовав `Scene` и расставив блоки через `applyLayout`.
   Барабаны, подсветка, кнопки и счётчики берутся из SDK как есть.
5. Экспортировать описание игры:

```ts
export const myGame = {
  background: THEME.backdrop,
  async start(app) {
    const loading = new LoadingScene()
    await app.scenes.goTo(loading)
    await loadAssets(GAME_ASSETS, (progress) => loading.setProgress(progress))
    await app.scenes.goTo(new MyScene(/* ... */))
  },
} satisfies GameDefinition
```

6. Поменять один импорт в `src/main.ts`.

Точка входа про игру больше ничего не знает: ни про символы, ни про ресурсы,
ни про сцены.

## Как подключить ресурсы

Файлы кладутся в `public/assets/`, строка — в манифест игры
`src/games/<id>/config/assets.ts`:

```ts
export const GAME_ASSETS: AssetManifest = [
  {
    alias: 'font-display',
    src: 'assets/fonts/orbitron.woff2',
    data: { family: 'Orbitron', weights: ['500', '800'] },
  },
]
```

Загрузку, прогресс и ожидание берёт на себя `loadAssets` из SDK.

Два правила:

- **Путь без ведущего слеша.** Браузер разрешает его относительно документа,
  поэтому сборка работает и в корне домена, и в подпапке.
- **Ресурсы грузятся до создания сцены.** Pixi измеряет текст в момент
  создания: если сделать это раньше загрузки шрифта, все подписи «прыгнут»
  после подмены. Поэтому в `start` сначала ресурсы, потом текстуры, и только
  затем сцена.

## Как настроить layout

Вся вёрстка экрана — один файл `src/games/<id>/config/layout.ts`. Для каждого
блока задаётся место в альбоме и в портрете, числа — доли экрана:

```ts
export const GAME_LAYOUT = {
  reels: {
    landscape: { x: 0.5, y: 0.44, fitWidth: 0.56, fitHeight: 0.56 },
    portrait: { x: 0.5, y: 0.29, fitWidth: 0.96, fitHeight: 0.36 },
  },
} satisfies LayoutScheme<'reels'>
```

Сцена применяет это одним вызовом:

```ts
override resize(viewport: Viewport): void {
  applyLayout(GAME_LAYOUT, viewport, this.blocks)
}
```

Поля `Placement`: `x` и `y` — куда поставить, `anchorX` и `anchorY` — какой
точкой блока (по умолчанию центром), `fitWidth` и `fitHeight` — в какую долю
экрана вписать, `area` — считать доли от всего экрана или от области без
системных отступов (по умолчанию второе).

Три правила, выведенные на практике:

- **Задавайте обе границы, `fitWidth` и `fitHeight`.** С одной границей блок на
  непривычных пропорциях вырастет по второй оси и наедет на соседей.
- **Блок объявляет свой размер через `boundsArea`.** Тогда раскладка не зависит
  от содержимого: ни длина числа в счётчике, ни положение ленты барабанов её
  не сдвигают.
- **У блоков одного ряда доля ширины пропорциональна проектной ширине.** Только
  тогда масштаб у них совпадает, а значит совпадает и высота на экране.
  В `config/layout.ts` эти доли поэтому вычисляются, а не вписаны числами.

Ориентация определяется по пропорциям экрана, а не по событию устройства.
Размер проверяется каждый кадр — так ловятся и поворот, и съезжающая адресная
строка мобильного браузера, которая событий не присылает.
